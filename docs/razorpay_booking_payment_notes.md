## 1. Database Models

**File:** [schema.prisma](file:///d:/FleetLink-A_Rental_App/backend/prisma/schema.prisma)

### Enums

```prisma
enum BookingStatus {
  PENDING            // Initial state (not used currently — we go straight to PAYMENT_PENDING)
  PAYMENT_PENDING    // Booking created, waiting for customer to pay (10-min hold)
  CONFIRMED          // Payment received via webhook → booking is locked in
  ACTIVE             // Vehicle has been picked up by customer (future feature)
  COMPLETED          // Vehicle returned, rental period over (future feature)
  CANCELLED          // Hold expired or customer cancelled (future feature)
  REJECTED           // Store owner rejected the booking (future feature)
}
```
- These statuses form a **state machine** — a booking can only transition in specific directions.
- Right now we use: `PAYMENT_PENDING → CONFIRMED` (via webhook).

```prisma
enum DepositStatus {
  HELD                // Security deposit collected, money is held
  REFUNDED            // Full refund after clean vehicle return
  PARTIALLY_REFUNDED  // Partial refund (damage deduction)
  FORFEITED           // No refund (severe damage)
}
```
- This is a **separate state machine** from `BookingStatus` — a booking can be `COMPLETED` but the deposit can still be `HELD` until inspection.

```prisma
enum PaymentStatus {
  PENDING   // Razorpay order created, customer hasn't paid yet
  SUCCESS   // Razorpay webhook confirmed payment was captured
  FAILED    // Payment failed (future: webhook for payment.failed)
}
```

### Booking Model

```prisma
model Booking {
  id             String        @id @default(uuid())
```
- **`id`**: Primary key, auto-generated UUID. Used in URLs like `POST /bookings/:id/pay`.

```prisma
  userId         String
  vehicleId      String
```
- **`userId`**: Which customer made this booking (references `User.id`).
- **`vehicleId`**: Which vehicle is being rented (references `Vehicle.id`).

```prisma
  startDate      DateTime      @db.Date
  endDate        DateTime      @db.Date
```
- **`@db.Date`**: Stores DATE only (no time component) in MySQL.
- **`endDate` is EXCLUSIVE** — it's the return date, not a billed day. A booking from Aug 1 to Aug 3 means 2 rental days (Aug 1 and Aug 2).

```prisma
  status         BookingStatus @default(PENDING)
  totalPrice     Decimal       @db.Decimal(10, 2)
```
- **`totalPrice`**: Final calculated price using the tiered pricing algorithm. `Decimal(10,2)` = up to 99,999,999.99.

```prisma
  idempotencyKey String        @unique
```
- **`idempotencyKey`**: A UUID generated by the **client** (frontend). Sent with every booking request.
  - If the client sends the same key twice (e.g., user double-clicks), the server returns the existing booking instead of creating a duplicate.
  - `@unique` constraint means if two concurrent requests somehow both pass the code check, the database itself will reject the second insert.

```prisma
  expiresAt      DateTime?
```
- **`expiresAt`**: Set to `NOW + 10 minutes` when booking is created.
  - Gives the customer 10 minutes to complete payment.
  - After expiry, the booking should be cleaned up by a background job (not built yet).
  - `?` means nullable — only relevant when status is `PAYMENT_PENDING`.

```prisma
  maintenanceFeeCharged  Decimal @db.Decimal(10, 2)
  securityDepositCharged Decimal @db.Decimal(10, 2)
```
- **Price snapshots**: These capture the vehicle's maintenance fee and security deposit **at the time of booking**.
  - If the store owner later changes the vehicle's fees, existing bookings are not affected.
  - This is a common e-commerce pattern called "freezing the price at order time."

```prisma
  depositStatus       DepositStatus?
  depositRefundAmount Decimal?       @db.Decimal(10, 2)
  damageNotes         String?        @db.Text
```
- **Deposit lifecycle fields**:
  - `depositStatus`: Starts as `null`, set to `HELD` when payment succeeds (via webhook).
  - `depositRefundAmount`: How much was refunded (if partially refunded).
  - `damageNotes`: Text notes about vehicle damage (for partial refund/forfeiture).

```prisma
  @@index([vehicleId, status])
```
- **Composite index**: Speeds up the critical query "find all active/pending bookings for this vehicle."
  - Without this index, the overlap check would do a full table scan on every booking request.

### Payment Model

```prisma
model Payment {
  id                String        @id @default(uuid())
  bookingId         String        @unique
```
- **`bookingId @unique`**: Enforces **one-to-one** relationship. A booking can have exactly one payment.

```prisma
  razorpayOrderId   String        @unique
```
- **`razorpayOrderId`**: The `order_XXXXXXXXXXXXXX` ID returned by Razorpay when we create an order.
  - `@unique` ensures we can look it up efficiently when the webhook arrives.
  - This is our **join key** between our system and Razorpay's system.

```prisma
  razorpayPaymentId String?       @unique
```
- **`razorpayPaymentId`**: The `pay_XXXXXXXXXXXXXX` ID.
  - **Starts as `null`** — we don't know it when we create the order.
  - Gets filled in by the **webhook** when Razorpay confirms the payment was captured.
  - `@unique` prevents processing the same payment twice.

```prisma
  amount            Decimal       @db.Decimal(10, 2)
  status            PaymentStatus @default(PENDING)
```
- **`amount`**: Stored in rupees (not paise). Matches `booking.totalPrice`.
- **`status`**: Starts as `PENDING`, transitions to `SUCCESS` when the webhook confirms capture.

## 2. Razorpay Client Config

**File:** [razorpay.js](file:///d:/FleetLink-A_Rental_App/backend/src/config/razorpay.js)

```js
const Razorpay = require('razorpay');
```
- Imports the official `razorpay` npm package. This is Razorpay's Node.js SDK.

```js
const keyId = process.env.RAZORPAY_KEY_ID;
const keySecret = process.env.RAZORPAY_KEY_SECRET;
```
- Reads credentials from environment variables (stored in `.env`).
  - `RAZORPAY_KEY_ID` looks like `rzp_test_XXXXXXXXXXXX`
  - `RAZORPAY_KEY_SECRET` looks like a long alphanumeric string
- These are **test mode** keys from the Razorpay Dashboard.

```js
if (!keyId || !keySecret) {
  console.warn(
    '⚠️  RAZORPAY_KEY_ID or RAZORPAY_KEY_SECRET not set in .env — payment endpoints will fail'
  );
}
```
- **Soft warning**: Server still starts, but payment endpoints will fail with Razorpay API errors.
- This is intentional — other parts of the app (stores, vehicles) can still work without payment keys.

```js
if (keyId && !keyId.startsWith('rzp_test_')) {
  throw new Error(
    'FATAL: RAZORPAY_KEY_ID must be a test key (rzp_test_...). ' +
    'Live keys are not allowed in development.'
  );
}
```
- **Safety guard**: Prevents accidentally using production/live Razorpay keys during development.
  - Live keys start with `rzp_live_` and charge real money.
  - Test keys start with `rzp_test_` and use Razorpay's sandbox (no real charges).
  - If someone pastes a live key, the server **crashes immediately** with a clear error.

```js
const razorpay = new Razorpay({
  key_id: keyId || '',
  key_secret: keySecret || '',
});

module.exports = razorpay;
```
- Creates a **singleton** Razorpay client instance.
- `|| ''` prevents `undefined` from being passed (Razorpay SDK might throw a cryptic error otherwise).
- Exported so other files can do `const razorpay = require('../config/razorpay')` and call methods like `razorpay.orders.create()`.

## 3. Booking Routes

**File:** [bookingRoutes.js](file:///d:/FleetLink-A_Rental_App/backend/src/routes/bookingRoutes.js)

```js
const express = require('express');
const { requireAuth, requireRole } = require('../middleware/auth');
const { createBooking } = require('../controllers/bookingController');
const { initiatePayment } = require('../controllers/paymentController');
```
- Imports:
  - `requireAuth`: Middleware that checks Clerk JWT → syncs user to local DB → sets `req.user`.
  - `requireRole('CUSTOMER')`: Ensures only customers (not store owners/admins) can create bookings.
  - `createBooking`: The booking creation handler.
  - `initiatePayment`: The Razorpay order creation handler.

```js
const router = express.Router();
```
- Creates an Express sub-router. All routes here are relative — the prefix `/api/v1/bookings` is added in `app.js`.

```js
router.post('/', requireAuth, requireRole('CUSTOMER'), createBooking);
```
- **`POST /api/v1/bookings`** — Create a new booking.
- Middleware pipeline runs left-to-right:
  1. `requireAuth` → Verifies JWT, syncs user, sets `req.user`
  2. `requireRole('CUSTOMER')` → Checks `req.user.role === 'CUSTOMER'`, rejects store owners/admins
  3. `createBooking` → The actual controller logic

```js
router.post('/:id/pay', requireAuth, initiatePayment);
```
- **`POST /api/v1/bookings/:id/pay`** — Create a Razorpay order for a booking.
- No `requireRole` — ownership is checked **inside** `initiatePayment` instead.
  - Why? Because the role is always CUSTOMER for this action, but the critical check is "does this booking belong to the requesting user?" which is more nuanced than a role check.
- `:id` is the booking UUID, accessible via `req.params.id` in the controller.

### Controller Function (Lines 14–126)


#### Step 1: Fetch Booking with Ownership Check (Lines 16–31)

```js
    const bookingId = req.params.id;
```
- Extracts the booking ID from the URL: `/api/v1/bookings/abc-123-def/pay` → `bookingId = 'abc-123-def'`.

```js
    const booking = await prisma.booking.findFirst({
      where: {
        id: bookingId,
        userId: req.user.id,   // ← OWNERSHIP CHECK
      },
      include: { payment: true },
    });
```
- **`findFirst` with two conditions**: Finds a booking that matches BOTH the ID **and** belongs to the current user.
- **Security**: If User A tries to pay for User B's booking, this returns `null` — same as if the booking doesn't exist.
  - This prevents **booking ID enumeration** — an attacker can't probe random UUIDs to discover other users' bookings.
- **`include: { payment: true }`**: Eagerly loads the related Payment record (if one exists). We need this for the idempotency check.

```js
    if (!booking) {
      throw new ApiError(404, 'Booking not found');
    }
```
- Same 404 for "doesn't exist" and "not yours" — intentionally vague for security.

#### Step 2: Status Validation (Lines 33–46)

```js
    if (booking.status !== 'PAYMENT_PENDING') {
      const messages = {
        CONFIRMED: 'This booking is already paid and confirmed',
        ACTIVE: 'This booking is already active',
        COMPLETED: 'This booking has already been completed',
        CANCELLED: 'This booking was cancelled — please create a new booking',
        PENDING: 'This booking is in an unexpected state — contact support',
      };
      throw new ApiError(
        400,
        messages[booking.status] || `Cannot pay for a booking with status: ${booking.status}`
      );
    }
```
- Only `PAYMENT_PENDING` bookings can be paid for.
- The `messages` object provides **human-readable error messages** for each possible wrong state.
- The fallback `|| '...'` handles any new status values that might be added in the future.
- **Why this matters**: Prevents paying twice for the same booking, paying for cancelled bookings, etc.

#### Step 3: Expiry Check (Lines 48–59)

```js
    if (booking.expiresAt && new Date(booking.expiresAt) <= new Date()) {
      throw new ApiError(
        410,
        'This booking hold has expired — please create a new booking',
        [`Hold expired at: ${booking.expiresAt.toISOString()}`]
      );
    }
```
- **`410 Gone`**: HTTP status code meaning "the resource existed but is no longer available."
- Even if the background cleanup job hasn't run yet to mark this booking as `CANCELLED`, we **proactively reject** expired holds.
- `new Date(booking.expiresAt) <= new Date()` = "has the expiry time passed?"
- Without this, a customer could pay for a booking that logically expired 30 minutes ago (because the cleanup cron hasn't run yet), which would be unfair to another customer who might be trying to book the same dates.

#### Step 4: Idempotency — Return Existing Payment (Lines 61–80)

```js
    if (booking.payment) {
```
- Remember: we did `include: { payment: true }`. If a Payment record already exists for this booking, `booking.payment` will be populated.

```js
      if (booking.payment.status === 'SUCCESS') {
        throw new ApiError(400, 'Payment has already been completed for this booking');
      }
```
- If the payment is already confirmed (via webhook), don't let them pay again.

```js
      return res.status(200).json(
        new ApiResponse(200, {
          orderId: booking.payment.razorpayOrderId,
          razorpayKey: process.env.RAZORPAY_KEY_ID,
          amount: Math.round(Number(booking.totalPrice) * 100),
          currency: 'INR',
          bookingId: booking.id,
        }, 'Payment order already exists — use this to complete checkout')
      );
```
- **Idempotent replay**: If the frontend called `/pay` before (creating a Razorpay order) and is calling again (e.g., page refresh, network retry), we return the **same order ID**.
  - No duplicate Razorpay order is created.
  - The frontend gets the data it needs to re-open the Razorpay checkout widget.
- **`200`** instead of `201` to signal "this was already created, I'm returning the existing one."

#### Step 5: Convert to Paise (Lines 82–89)

```js
    const amountInPaise = Math.round(Number(booking.totalPrice) * 100);
```
- **Razorpay expects amounts in the smallest currency unit** (paise for INR, cents for USD).
  - ₹500.00 → 50000 paise
  - ₹35.85 → 3585 paise
- **Why `Math.round`?**:
  - JavaScript floating-point arithmetic can produce results like `35.85 * 100 = 3584.9999999999995`.
  - `Math.round` snaps this back to `3585`.
  - `Number()` converts Prisma's `Decimal` type to a JS number.

- **`receipt`**: A reference ID for our records — we use our booking ID.

- **`notes`**: Arbitrary metadata attached to the order. Visible in Razorpay Dashboard and included in webhook payloads.

## 5. Webhook Controller — Line by Line

**File:** [webhookController.js](file:///d:/FleetLink-A_Rental_App/backend/src/controllers/webhookController.js)

> [!CAUTION]
> This is the **highest-risk file** in the payment module. A bug here can result in:
> - Confirming bookings that were never paid (if signature verification is bypassed)
> - Missing payments (if the webhook is rejected incorrectly)
> - Double-charging or double-confirming (if idempotency is broken)

### Why Webhooks?

The payment flow is **asynchronous**:
1. Our server creates a Razorpay order → returns order ID to frontend.
2. Frontend opens Razorpay's checkout widget → customer enters card/UPI details.
3. Razorpay processes the payment on their servers.
4. Razorpay sends a **webhook** (HTTP POST) to our server with the payment result.

We **cannot trust the frontend** to tell us "payment succeeded" because:
- A malicious user could fake this call.
- The frontend might crash or lose connection after payment.
- Razorpay's webhook is the **single source of truth**.

### Imports (Line 18–19)

```js
const crypto = require('crypto');
const prisma = require('../config/prisma');
```
- **`crypto`**: Node.js built-in module for cryptographic operations. Used for HMAC-SHA256 signature verification.
- **`prisma`**: Database client.
- Notice: **No `razorpay` SDK import** — we don't call any Razorpay API here. We're only receiving and verifying data.

### Handler Function (Line 21)

```js
const handleWebhook = async (req, res) => {
```
- No `next` parameter — we **never** forward to the error handler.
  - Why? Razorpay retries webhooks that get non-2xx responses. If our error handler returns 500, Razorpay will keep retrying for hours.
  - Instead, we handle all errors explicitly and always return a response.

### STEP 1: Signature Verification (Lines 22–72)

> [!IMPORTANT]
> This MUST happen **before** reading any payload data. If we branched on event type first, an attacker could craft a fake payload and bypass verification.

```js
  const webhookSecret = process.env.RAZORPAY_WEBHOOK_SECRET;
```
- The webhook secret is a shared secret between Razorpay and our server.
  - Set in the Razorpay Dashboard when configuring the webhook URL.
  - Stored in our `.env` file.
  - **Never exposed to the frontend.**

```js
  const receivedSignature = req.headers['x-razorpay-signature'];
```
- Razorpay sends the HMAC signature in this HTTP header with every webhook call.

```js
  if (!receivedSignature) {
    return res.status(400).json({ error: 'Missing x-razorpay-signature header' });
  }
```
- If the header is missing, this isn't a legitimate Razorpay request.

```js
  if (!webhookSecret) {
    console.error('FATAL: RAZORPAY_WEBHOOK_SECRET is not configured');
    return res.status(500).json({ error: 'Webhook secret not configured' });
  }
```
- Server misconfiguration — we can't verify anything without the secret.

```js
  const rawBody = req.body;
```
- **`req.body` is a Buffer, NOT a JS object.**
  - This route uses `express.raw()` (configured in `app.js`), not `express.json()`.
  - We need the exact bytes that Razorpay signed, byte-for-byte.
  - If `express.json()` parsed it first, the re-serialized JSON might differ in whitespace, key ordering, or Unicode escaping — breaking the signature.

```js
  const expectedSignature = crypto
    .createHmac('sha256', webhookSecret)
    .update(rawBody)
    .digest('hex');
```
- **How HMAC-SHA256 works:**
  1. `createHmac('sha256', webhookSecret)` — Creates an HMAC calculator using SHA-256 and our secret key.
  2. `.update(rawBody)` — Feeds the raw request body bytes into the calculator.
  3. `.digest('hex')` — Outputs the HMAC as a 64-character hex string.
- **The logic**: Razorpay computed `HMAC(secret, body)` on their end and sent the result as `x-razorpay-signature`. We compute the same thing. If they match, the payload wasn't tampered with and came from someone who knows the secret (Razorpay).

```js
  const expectedBuf = Buffer.from(expectedSignature, 'hex');
  const receivedBuf = Buffer.from(receivedSignature, 'hex');
```
- Converts both hex strings to Buffers for comparison.

```js
  if (expectedBuf.length !== receivedBuf.length) {
    console.warn('Webhook signature length mismatch — rejecting');
    return res.status(400).json({ error: 'Invalid signature' });
  }
```
- **Length pre-check**: `timingSafeEqual` throws an error if the buffers are different lengths.
  - SHA-256 output is always 32 bytes (64 hex chars), so a length mismatch means the signature is garbage.

```js
  if (!crypto.timingSafeEqual(expectedBuf, receivedBuf)) {
    console.warn('Webhook signature mismatch — rejecting');
    return res.status(400).json({ error: 'Invalid signature' });
  }
```
- **`timingSafeEqual`**: Compares two buffers in **constant time**.
  - A normal `===` comparison returns `false` as soon as it hits the first mismatched byte. An attacker can measure how long the comparison takes to deduce which bytes are correct (**timing oracle attack**).
  - `timingSafeEqual` always compares ALL bytes, taking the same time regardless of where the mismatch is.

### Signature Verified — Safe Zone (Line 74+)

```js
  // Signature verified — payload is trustworthy from here on
```
- From this point, we can trust that the data came from Razorpay and wasn't modified in transit.

### Parse JSON (Lines 79–85)

```js
  let event;
  try {
    event = JSON.parse(rawBody.toString('utf8'));
  } catch (err) {
    console.error('Webhook body is not valid JSON:', err.message);
    return res.status(400).json({ error: 'Invalid JSON body' });
  }
```
- Now that we've verified the signature, we parse the raw bytes into a JS object.
- `rawBody.toString('utf8')` converts the Buffer to a string first.
- We wrap in `try/catch` because even though Razorpay should always send valid JSON, defensive coding is critical in the highest-risk file.

### STEP 2: Event Type Filter (Lines 87–97)

```js
  if (event.event !== 'payment.captured') {
    return res.status(200).json({ status: 'ignored', event: event.event });
  }
```
- Razorpay sends many event types:
  - `payment.authorized` — Payment authorized but not yet captured
  - `payment.captured` — Money actually taken from customer's account ✅
  - `payment.failed` — Payment attempt failed
  - `order.paid` — Order fully paid
  - `refund.processed` — Refund completed
  - etc.
- **We only act on `payment.captured`** — this is when money has actually moved.
- For all other events, we return `200 OK` so Razorpay stops retrying.
  - Returning `4xx` or `5xx` for ignored events would cause unnecessary retries.

### STEP 3: Extract IDs (Lines 99–116)

```js
  const paymentEntity = event.payload?.payment?.entity;
```
- Razorpay's webhook payload structure:
  ```json
  {
    "event": "payment.captured",
    "payload": {
      "payment": {
        "entity": {
          "id": "pay_XXXXXXXXXXXXXX",
          "order_id": "order_XXXXXXXXXXXXXX",
          "amount": 50000,
          ...
        }
      }
    }
  }
  ```
- `?.` (optional chaining) prevents crashes if the structure is unexpected.

```js
  if (!paymentEntity) {
    console.error('Webhook payload missing payment entity');
    return res.status(400).json({ error: 'Malformed payload: missing payment entity' });
  }
```
- Defensive check — should never happen with real Razorpay payloads, but we handle it.

```js
  const razorpayPaymentId = paymentEntity.id;
  const razorpayOrderId = paymentEntity.order_id;
```
- **`razorpayPaymentId`** (`pay_XXXX`): Identifies this specific payment transaction.
- **`razorpayOrderId`** (`order_XXXX`): Links back to the order we created in the payment controller.

```js
  if (!razorpayPaymentId || !razorpayOrderId) {
    console.error('Webhook payload missing payment or order ID');
    return res.status(400).json({ error: 'Malformed payload: missing IDs' });
  }
```
- Both IDs are required to process the webhook.

### STEP 4: Idempotency Check (Lines 118–131)

```js
  const existingPayment = await prisma.payment.findFirst({
    where: { razorpayPaymentId },
  });

  if (existingPayment) {
    return res.status(200).json({ status: 'already_processed', paymentId: existingPayment.id });
  }
```
- **Why idempotency matters**: Razorpay retries webhooks if they don't get a `2xx` response. Even after getting a `200`, network issues might cause Razorpay to think the response was lost and retry.
- If we already stored this `razorpayPaymentId`, the payment was already processed — return `200` immediately.
- Without this, a retry could attempt to update the booking twice, potentially causing database errors or inconsistent state.

### STEP 5: Find Payment by Order ID (Lines 133–154)

```js
  const payment = await prisma.payment.findUnique({
    where: { razorpayOrderId },
    include: { booking: true },
  });
```
- Looks up our `Payment` record using the Razorpay order ID as the key.
  - This was created by the payment controller in Step 7 of Section 4.
- `include: { booking: true }` loads the related booking so we can update it in the next step.

```js
  if (!payment) {
    console.error(`Webhook: no Payment found for razorpayOrderId ${razorpayOrderId}`);
    return res.status(200).json({ status: 'no_matching_order' });
  }
```
- **Return `200` even for unmatched orders**: If the order doesn't exist in our DB (e.g., created outside our system, DB wiped), returning a `4xx`/`5xx` would cause Razorpay to retry forever for something we can never fix.
- We log the error for debugging.

```js
  if (payment.status === 'SUCCESS') {
    return res.status(200).json({ status: 'already_processed' });
  }
```
- Edge case: The payment was already marked as `SUCCESS` (maybe the `razorpayPaymentId` was stored in a different format or the idempotency check above didn't catch it). Belt-and-suspenders safety.

### STEP 6: Atomic Update — Payment + Booking (Lines 156–190)

```js
  try {
    await prisma.$transaction([
      prisma.payment.update({
        where: { id: payment.id },
        data: {
          razorpayPaymentId,
          status: 'SUCCESS',
        },
      }),
      prisma.booking.update({
        where: { id: payment.bookingId },
        data: {
          status: 'CONFIRMED',
          depositStatus: 'HELD',
        },
      }),
    ]);
```
- **`prisma.$transaction([...])`**: Batch transaction — either **both** updates succeed or **neither** does.
  - If the booking update fails, the payment update is rolled back too.
  - This prevents a scenario where Payment = SUCCESS but Booking is still PAYMENT_PENDING.
- **Payment update**:
  - Sets `razorpayPaymentId` (previously `null`) — now we have the complete link to Razorpay.
  - Changes `status` from `PENDING` → `SUCCESS`.
- **Booking update**:
  - Changes `status` from `PAYMENT_PENDING` → `CONFIRMED` — the vehicle is now officially reserved.
  - Sets `depositStatus` to `HELD` — the security deposit is now being held.

```js
    console.log(
      `✅ Payment confirmed: booking=${payment.bookingId} razorpayPayment=${razorpayPaymentId}`
    );

    return res.status(200).json({ status: 'processed', bookingId: payment.bookingId });
```
- Success! Log the confirmation and tell Razorpay we processed it.

```js
  } catch (err) {
    console.error('Webhook processing error:', err);
    return res.status(500).json({ error: 'Internal processing error' });
  }
```
- If the database transaction fails, return `500` so **Razorpay retries** the webhook.
  - This is the correct behavior — the error is temporary (e.g., DB connection issue) and the next retry might succeed.
  - This is different from "no matching order" where we return `200` because retrying won't help.

## 6. App.js — Middleware & Route Registration

**File:** [app.js](file:///d:/FleetLink-A_Rental_App/backend/src/app.js)

The critical webhook-related section:

```js
// ── Razorpay Webhook — MUST be BEFORE express.json() ─────
app.post(
  '/api/v1/webhooks/razorpay',
  express.raw({ type: 'application/json' }),
  handleWebhook
);

// ── JSON body parsing for all other routes ───────────────
app.use(express.json());
```

> [!WARNING]
> **The ordering here is CRITICAL.** The webhook route MUST be registered **before** `express.json()`.

**Why?**
- `express.json()` reads the entire request body, parses it as JSON, and replaces `req.body` with the parsed JS object.
- Once `express.json()` has consumed the raw bytes, they're gone. You cannot reconstruct the exact original bytes from the parsed object (JSON serialization is not byte-level deterministic — key ordering, whitespace, etc. may differ).
- The HMAC signature was computed over the **exact raw bytes** Razorpay sent. We need those exact bytes.

**How Express middleware ordering works:**
1. Request arrives: `POST /api/v1/webhooks/razorpay`
2. Express checks routes **in registration order**.
3. It finds `app.post('/api/v1/webhooks/razorpay', ...)` FIRST.
4. `express.raw({ type: 'application/json' })` reads the body as a raw Buffer → sets `req.body` to a Buffer.
5. `handleWebhook` runs, sends a response.
6. Because a response was sent, `express.json()` (registered below) **never runs** for this request.

For all OTHER routes:
1. No early route matches → falls through to `app.use(express.json())`.
2. `express.json()` parses the body as JSON → sets `req.body` to a JS object.
3. Normal controllers work with parsed objects as expected.

## 7. Complete Payment Flow — End to End

Here's the full journey of a booking payment:

```
┌─────────────────────────────────────────────────────────────────────┐
│                    COMPLETE PAYMENT FLOW                            │
└─────────────────────────────────────────────────────────────────────┘

STEP 1: Customer creates a booking
────────────────────────────────────
  Frontend → POST /api/v1/bookings
  Body: { vehicleId, startDate, endDate, idempotencyKey }
  
  Server:
    ├── Lock vehicle row (SELECT ... FOR UPDATE)
    ├── Check vehicle status = AVAILABLE
    ├── Check idempotencyKey not used
    ├── Check no date overlap with existing bookings
    ├── Calculate tiered price
    ├── Snapshot maintenance fee + security deposit
    └── INSERT Booking (status: PAYMENT_PENDING, expiresAt: NOW + 10min)
  
  Response: { booking, pricing }

          │
          ▼

STEP 2: Customer initiates payment
────────────────────────────────────
  Frontend → POST /api/v1/bookings/:id/pay
  
  Server:
    ├── Verify booking exists + belongs to user
    ├── Verify status = PAYMENT_PENDING
    ├── Verify hold hasn't expired
    ├── Check if Payment already exists (idempotency)
    ├── Convert totalPrice to paise
    ├── Call razorpay.orders.create()
    └── INSERT Payment (status: PENDING, razorpayPaymentId: null)
  
  Response: { orderId, razorpayKey, amount, currency, bookingId }

          │
          ▼

STEP 3: Customer pays via Razorpay widget
──────────────────────────────────────────
  Frontend opens Razorpay Checkout Widget with:
    - key: razorpayKey
    - order_id: orderId
    - amount: amount
  
  Customer enters payment details (card/UPI/netbanking).
  Razorpay processes payment on their servers.
  
  (Our server is NOT involved in this step)

          │
          ▼

STEP 4: Razorpay sends webhook to our server
─────────────────────────────────────────────
  Razorpay → POST /api/v1/webhooks/razorpay
  Headers: { x-razorpay-signature: "HMAC-SHA256 hash" }
  Body: Raw JSON with event: "payment.captured"
  
  Server:
    ├── Verify HMAC signature (reject if forged)
    ├── Parse JSON from raw bytes
    ├── Filter: only process payment.captured
    ├── Extract razorpayPaymentId + razorpayOrderId
    ├── Idempotency: skip if already processed
    ├── Find Payment by razorpayOrderId
    └── ATOMIC TRANSACTION:
        ├── UPDATE Payment: razorpayPaymentId = pay_XXX, status = SUCCESS
        └── UPDATE Booking: status = CONFIRMED, depositStatus = HELD
  
  Response: { status: "processed" }

          │
          ▼

RESULT: Booking is CONFIRMED, vehicle is reserved! 🎉
```

### Key Security Properties

| Property | How It's Achieved |
|:---|:---|
| **No double bookings** | `SELECT ... FOR UPDATE` + date overlap check in transaction |
| **No double payments** | `idempotencyKey` on Booking + existing Payment check |
| **No forged webhooks** | HMAC-SHA256 signature verification before any payload processing |
| **No timing attacks** | `crypto.timingSafeEqual` for signature comparison |
| **No live-key accidents** | `rzp_test_` prefix validation in razorpay.js |
| **No partial updates** | `prisma.$transaction` for atomic Payment + Booking update |
| **No stale holds** | `expiresAt` check in payment controller |
| **No ID enumeration** | Ownership check baked into findFirst query |
